# 与原版 fnos-lxc 的差异

原项目：[mg6630/fnos-lxc](https://github.com/mg6630/fnos-lxc)（MIT）
本项目：[ansekafei/fnos-lxc-manager](https://github.com/ansekafei/fnos-lxc-manager)（MIT）

原版 README 第一句写的是「**基于 ZFS** 提供容器生命周期管理」，这是最大的门槛：没有 ZFS 池的机器装上也用不了，安装向导会直接显示「无可用 ZFS 池」。

本项目把存储后端整个换掉了，同时补齐了一批原版缺的创建选项。

---

## 一、存储后端：ZFS → btrfs 子卷

| | 原版 | 本项目 |
|---|---|---|
| 前置条件 | 必须有 ZFS 池（`zpool list` 能列出来） | 任意 btrfs 卷；没有 btrfs 也能跑（退化为普通目录） |
| rootfs | ZFS dataset | btrfs 子卷 `{LXC_PATH}/{name}/rootfs` |
| LXC 配置 | `lxc.rootfs.path = zfs:<dataset>` | `lxc.rootfs.path = dir:<绝对路径>` |
| 快照 | `zfs snapshot` | 只读子卷 `.snapshots/{snap}` |
| 克隆 | `zfs clone` | `btrfs subvolume snapshot` |
| 回滚 | `zfs rollback` | 删 rootfs → 从快照重新 snapshot |
| 备份 | `zfs send \| xz` | `btrfs send \| xz`（沿用 `.zfs.xz` 后缀） |
| 恢复 | `zfs receive` | `xz -dc \| btrfs receive` |

**为什么用 `dir:` 而不是 btrfs 驱动**：LXC 的 btrfs 后端在不同版本行为不一致（`lxc.btrfs.root` 的语义改过），而 `dir:` 后端只是「把路径当普通目录用」，兼容性最好，btrfs 的特性全部由我们自己用 `btrfs` 命令操作，LXC 完全不需要懂 btrfs。

**没有 btrfs 会怎样**：容器照常创建、启停、进控制台，只是快照/克隆/备份会明确报错「当前存储卷不是 btrfs」。不会假装成功。

## 二、网络：修掉 macvlan 挂 OVS 桥不通的坑

原版创建容器时 bridge 模式用的是 `lxc.net.0.type = macvlan`。macvlan 挂在 OVS 桥上**流量进桥就丢**——DHCP 能拿到地址，但 ping 不通、出不了网。这个坑很难自己看出来，因为容器里 `ip addr` 显示一切正常。

本项目改成：

```
lxc.net.0.type = veth
lxc.net.0.link = <OVS 桥名或物理网卡>
lxc.net.0.flags = up
```

**为什么这样就够**：LXC 5.0.2 的 `src/lxc/network.c:2735` 有个 `is_ovs_bridge()`——只要 `/sys/class/net/<桥名>/bridge` 不存在，就判定为 OVS 桥，然后 `network.c:2822` 自动执行 `ovs-vsctl add-port`，停止时 `lxc_ovs_delete_port` 自动 `del-port`。

所以**不需要 hook、不需要重编 liblxc**。Debian 官方包直接支持。早期我以为要开 `HAVE_OVS` 重编，后来查源码发现 upstream 从来没有 `lxc.net.0.veth.mode = ovs` 这个配置项，原生支持走的是自动探测这条路。

## 三、新增的创建选项（原版没有）

原版创建容器只有：名称、模板、自启动、网络模式。本项目对齐 PVE 创建 CT 的流程：

| 分组 | 选项 |
|---|---|
| 常规 | 容器名称、模板、主机名、自启动 |
| 资源 | 内存（MB）、Swap（MB）、CPU 核心数、CPU 限制（%） |
| 网络 | 模式（bridge/nat）、MAC、IPv4 配置（DHCP/静态）、IPv4 地址、IPv4 网关、IPv6 配置（SLAAC/静态/无）、IPv6 地址、IPv6 网关、VLAN Tag、MTU |
| DNS | 搜索域、DNS 服务器 |
| 访问 | Root 密码、SSH 公钥（支持读取 `.pub` 文件） |
| 其他 | 环境变量（每行 `KEY=VALUE`） |

资源限制写的是 cgroup2：

```
lxc.cgroup2.memory.max      = 512M
lxc.cgroup2.memory.swap.max = 512M
lxc.cgroup2.cpuset.cpus     = 0-3
lxc.cgroup2.cpu.max         = 200000 100000    # 200% = 2 核
```

**静态 IP 有个坑修过**：一开始写完 `lxc.net.0.ipv4.address` 之后，后面又无条件调了一次「往 rootfs 写 DHCP 配置」，把静态配置覆盖回去了。表现是「明明填了 192.168.1.240，容器拿到的是 DHCP 的 192.168.1.151」。现在只在没填静态地址时才写 DHCP。

**固定 MAC 的意义**：IPv6 是 EUI-64 由 MAC 推导的，固定 MAC 等于同时固定了 IPv4（DHCP 保留）和 IPv6 后缀。创建时生成 `00:16:3e:xx:xx:xx` 并落盘，之后可以在容器详情页改。

## 四、控制台兼容 Alpine

原版 `handle_terminal` 写死 `lxc-attach -n <name> -- /bin/bash -l`。Alpine 没有 bash，点终端直接进不去。

现在按顺序探测：`/bin/bash` → `/bin/sh` → `/bin/ash`。

## 六、应用中心升级兼容（这是原版装上去更新必崩的原因）

原版有三个问题，任意一个都会让「检查更新 / 升级 / 卸载」报「服务异常」：

| 问题 | 原版 | 后果 |
|---|---|---|
| `desktop_applaunchname` 大小写 | `fnlxc.APPLICATION`（全大写） | 应用中心按 `<appname>.Application` 驼峰匹配桌面入口，匹配不上拿到 nil → `appenvs.New` 空指针 → check 每 30 秒崩一次 |
| `config/privilege` 声明了不存在的用户 | `"username": "fnlxc"`，但系统里没有这个用户 | 升级时按声明查用户拿到 nil → 崩在 `InstallFileToDisk` |
| 安装前跑 apt | `install_init` 里 `apt-get install lxc lxc-templates lxcfs bridge-utils` | 实测 95 秒，超过应用中心对 install_init 的时限 → 任务被 cancel → 回滚 |

修复方式：驼峰改名、privilege 改成只有 `{"defaults":{"run-as":"root"}}`、apt 挪到 `install_callback`（安装后阶段，没有时限）。

**还有一个坑**：`appname` 一旦用过，应用中心内部会留标记（PostgreSQL 里查不到），清库清目录都去不掉。如果升级一直崩，换个 appname 是最干净的解法——本项目就是因为这个从 `fnlxc` 改名成了 `lxcmanager`。

## 七、打包方式

原版 `build.sh` 只 `cp server/fnlxc.py`，没有 `app.tgz` 的 MD5 校验，manifest 里也没有 `checksum` 字段。

本项目：

- `app/` 组装成 `app.tgz`，算 MD5 写进 manifest 的 `checksum`
- 根目录（`manifest` `cmd/` `config/` `wizard/` `ICON*.PNG`）单独打一层 tar
- 目录权限 755、文件权限 644、`cmd/*` 和 `wizard/install` 可执行（原版打出来的目录是 `drw-r--r--`，没有 x 位，应用中心进不去）
- 图标 256×256 正方形（原版 120×111，桌面图标不渲染）

## 安装要求

| 项 | 要求 |
|---|---|
| 系统 | 飞牛 fnOS（x86_64） |
| LXC | `lxc` 包（应用会在安装后自动 `apt install lxc lxc-templates lxcfs bridge-utils`） |
| 存储 | 建议放在 btrfs 卷上（如 `/vol1/1000/lxc`）；非 btrfs 也能跑，只是没有快照/备份 |
| 网络 | 桥接模式需要宿主有 OVS 桥或普通网桥；NAT 模式用 `lxcbr0` |

## 已知限制

- **没有 btrfs 就没有快照/克隆/备份**，只有基础容器功能
- **应用内不能自动更新**，第三方包不在商店里，`check-update` 恒返回「无更新」；升级靠应用中心「手动安装」上传新包
- **VLAN/MTU 是高级选项**，填错会导致容器网络起不来，不确定就留空
- **OVS 桥被外部重建时**（比如飞牛网络页重新应用配置），容器可能断网，重启容器恢复
