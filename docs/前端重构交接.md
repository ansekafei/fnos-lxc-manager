## 一、为什么要重写

现有前端是随项目继承来的，长期打补丁后已经难以维护：

| 文件 | 行数 | 问题 |
|---|---|---|
| `ui/app.js` | 2244 | 129 个函数挤在同一作用域，无模块边界；渲染函数里直接发请求；全局可变状态散落 |
| `ui/style.css` | 1882 | 旧项目选择器与新布局混在一起，废弃规则未清理 |
| `ui/index.html` | 524 | 大量内联 `onclick="fn('名字')"`，容器名含特殊字符即失效 |

**根本问题**：结构按"页面长什么样"组织，而不是按"后端有什么"组织。于是每加一个功能都要在泥里再插一脚。继续修补的代价已高于重写。

## 二、已定决策（用户 m01172 拍板）

| 决策点 | 结论 |
|---|---|
| 技术栈 | **原生 ES Module**，零构建。`<script type="module">` 直跑，`release.sh` 不加任何构建步骤 |
| 文件分层 | **HTML / JS / CSS 三类分开**，JS 内部再按职责拆分目录 |
| 视觉 | **大分类栏位保留**（主从双栏骨架、左侧导航、四标签页的 tab 条），**标签页内部内容全部重做** |
| 迁移方式 | **一次性替换**，`ui/` 旧文件直接删除，不做新旧并存 |
| 契约来源 | **后端 API 为准**，`docs/API.md` 是唯一接口契约 |
| 执行时机 | 不在本会话，另开新会话 |

## 四、三条硬约束（用来根治当前问题）

1. **view 不直接发请求**。数据只从 `state` 进，动作只通过 `api/*` 出。现有"渲染函数里顺手 fetch"是抽象感的根源。
2. **一个接口一个函数**。函数名与 `docs/API.md` 第 2 节的表逐条对应，接口缺失在启动时就暴露，不用等点到按钮才发现。
3. **不写内联 `onclick`**。改事件委托 + `data-*` 属性，容器名走 `dataset`，杜绝转义地狱。

## 六、接口契约

以 `docs/API.md` 为准（本次会话产出，已与源码逐条核对）：

- 49 条路由注册 / 48 条唯一，除 `/api/health`（框架探活）外全部有前端调用
- 统一响应 `{success, data}` / `{success:false, error}`
- **HTTP 423 = 配置被 LXC 运行期锁定**，响应带 `locked:true`，UI 必须提示"停止容器后可编辑"
- 网关前缀 `/app/lxcmanager`，前端 `lxc()` → `/api/lxc`，`sys()` → `/api`

## 七、版本与发布

- 当前版本 **3.2.7**（`manifest` 与 `server/fnlxc.py:73` 的 `APP_VERSION` 已同步）
- 发版一律用 `./release.sh`：自动 patch+1 → 同步 manifest / APP_VERSION / 前端缓存戳 `?v=NNN` → 构建 → 包内核对 → 清理旧包（保留最近 5 个）
